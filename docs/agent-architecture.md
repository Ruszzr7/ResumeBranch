# Agent 架构与状态边界（Release 1）

本文记录 ResumeBranch Release 1 已实现的 Agent 架构，不是待实施方案。实际行为以 `backend/resume_agent.py`、`backend/harness/`、`backend/skills/` 和自动化测试为准。

## 设计目标

- 让模型根据用户意图决定回复、追问或请求修改，而不是把所有场景固化为单一路径。
- 给模型提供当前简历内容、JD、排版规则、对话记忆和按需视觉快照。
- 简单明确的修改优先走确定性路径，减少不必要的模型调用和格式损失。
- 所有 AI 修改先预览、后确认，保存时验证版本，避免过期覆盖。
- 主对话、命令对话和浏览器多标签页之间隔离上下文，并串行化同一简历的修改操作。
- 内部协议和英文标识保留在系统边界内，对外统一为项目组件对应的中文描述。

## 请求路由

LangGraph 的入口路由根据对话模式、确认协议和请求可解析程度选择节点：

```text
用户请求
  │
  ├─ 面试诊断 / 深度挖掘 / JD 复盘 ──> interview_coach
  │
  ├─ 确认或取消已有预览 ─────────────> tool_node
  │
  ├─ 可安全解析的明确修改 ───────────> direct_edit
  │
  └─ 普通咨询或复杂任务 ─────────────> conversation_llm
                                          │
                                          ├─ 直接回复或追问
                                          ├─ render_resume_pdf_images
                                          └─ request_resume_edit
                                                   │
                                                   ▼
                                               tool_node
                                                   │
                                                   ▼
                                              修改预览/结束
```

主要节点：

- `conversation_llm`：处理普通咨询和复杂任务；模型可直接回复，也可按需调用技能。
- `tool_node`：执行技能请求、组装预览，以及处理确认或取消后的状态推进。
- `direct_edit`：执行本地能够无歧义识别的字段替换、字号、排版和局部粗体修改。
- `interview_coach`：承载全面诊断、深度挖掘、JD 分析等求职辅导模式。
- `proposal_generator`：保留的兼容入口；正常修改由工具调用路径生成候选结果。

“面试”在这里指求职辅导对话模式，不是另一个登录或页面运行模式。

## 两个按需技能

### 简历修改技能

实现位于 `backend/skills/resume_edit.py`。

模型负责理解用户意图并提出结构化操作；技能本身不再次调用 LLM。它会：

1. 校验目标字段、布局能力和基础修订版本。
2. 在简历副本上应用结构化操作。
3. 规范化候选数据并返回差异与预览信息。
4. 等待用户确认，不直接写入正式简历。

这种分工避免模型直接拼接整份简历，也能在修改姓名等字段时保留原有的结构和局部格式信息。

### 简历页面快照技能

实现位于 `backend/skills/render_resume_pdf_images.py`。

该技能只读、按需调用。它使用与正式 PDF 导出相同的渲染源生成 PDF，再把有限页数转换为模型可读取的图片。快照在内存中传递，不修改简历，也不作为业务数据保存。

视觉快照用于回答分页、拥挤、留白和跨页等仅靠 JSON 难以可靠判断的问题；一般内容问答不会无条件渲染快照。

## 上下文与记忆

Harness 负责把本轮需要的信息组装给 Agent：

- 当前简历的结构化内容和排版配置。
- 当前岗位 JD 与任务信息。
- 当前对话窗口的近期消息、摘要和分层记忆。
- 修改中的修订版本、预览状态和占用状态。
- 必要时生成的页面视觉快照。

主对话和命令对话使用不同的上下文标识，消息历史与待确认状态不会相互混入。长对话可压缩为摘要，避免把完整历史无限加入每次模型请求。

## 状态存储边界

| 状态 | 存储位置 | 说明 |
|---|---|---|
| 用户、项目、简历、JD、对话 | SQLAlchemy 业务数据库 | 单用户配置（源码或安装包）为 SQLite，多用户配置为 MySQL |
| 导入原文件 | `data/source_documents/` 或容器应用数据卷 | 用于查看原版和继续处理 |
| 工作流控制检查点 | `data/langgraph_checkpoints.sqlite` | 保存必要的图执行状态，不替代业务数据库 |
| 运行中的临时预览 | 图状态与数据库中的确认元数据 | 确认、取消或失效后清理 |
| 页面视觉快照 | 内存 | 默认不持久化 |

业务数据不会因为关闭 LangGraph 检查点而消失。检查点数据库也不应被当作简历主数据的备份。

## 确认、过期检测与并发

修改请求进入候选预览前，会记录当前简历的修订版本和内容摘要。用户确认时再次比较：

- 一致：保存候选数据，产生新的修订版本，并保留撤销能力。
- 不一致：拒绝旧修改，返回统一中文提示，并让前端重新加载数据库中的正式简历。

同一简历的修改采用数据库级占用记录做串行化，覆盖以下来源：

- 主对话与命令对话同时请求修改。
- 同一浏览器的多个标签页。
- 多个后端请求或进程。

占用期间，另一个修改请求会收到“正在修改”类中文状态；普通咨询仍可继续。前端只用对话标签旁的状态灯展示少见的占用和待确认状态，不额外挤占页面空间。

多用户模式还实行单账号单活跃会话：同一账号在新设备登录后，旧会话在下一次请求时收到明确的重新登录提示。同一浏览器共享当前凭据的多个标签页仍需依赖上述简历修改锁，而不是依靠登录限制规避并发。

## 对外标识边界

Prompt 只声明通用规则：不得向用户暴露内部协议、字段路径、节点名、工具名或状态码。它不穷举所有英文标识。

可靠边界由三层共同保证：

1. 工具和节点返回结构化内部结果。
2. 后端在响应边界映射状态、错误和组件名称。
3. 前端只展示统一中文文案，并对异常响应使用中文兜底。

日志、测试和代码中可以保留稳定的英文内部标识，但弹窗、状态提示和正常对话回复不应直接显示这些标识。

## 兼容与演进约束

- 前端只依赖公开的 SSE 事件、确认结果和业务 API，不直接依赖图内部节点名。
- 增加技能时应保持“模型理解意图、技能确定性执行、确认后持久化”的边界。
- 增加新的直接修改语法时，只接受能够唯一定位且可保留格式的请求；模糊请求继续交给 Agent。
- 修改图状态结构时，应验证已有检查点和待确认数据的兼容性。
- 架构变更必须同步 `docs/testing.md` 中的自动与人工验收项。
