# Agent 架构与状态边界（Release 1）

本文记录 ResumeBranch Release 1 已实现的 Agent 架构，不是待实施方案。实际行为以 `backend/resume_agent.py`、`backend/harness/`、`.agents/skills/`、`backend/skill_runtime.py` 和自动化测试为准。

## 设计目标

- 让模型根据用户意图决定回复、追问或请求修改，而不是把所有场景固化为单一路径。
- 给模型提供当前简历内容、JD、排版规则、对话记忆和按需视觉快照。
- 简单明确的修改优先走确定性路径，减少不必要的模型调用和格式损失。
- 所有 AI 修改先预览、后确认，保存时验证版本，避免过期覆盖。
- 主对话、命令对话和浏览器多标签页之间隔离上下文，并串行化同一简历的修改操作。
- 内部协议和英文标识保留在系统边界内，对外统一为项目组件对应的中文描述。

## 请求路由

LangGraph 的入口路由根据教练 Skill 状态和请求可解析程度选择节点；候选确认不进入图，由 HTTP 确认端点统一处理：

```text
用户请求
  │
  ├─ 深度打磨 Command / 活跃教练 ───> conversation_llm
  │                                      │
  │                                  resume_coach
  │                                      │ 证据充分后请求用户授权
  │                                      └─ 授权后 resume_edit
  │
  ├─ 可安全解析的明确修改 ───────────> direct_edit
  │                                      │ 将确定性结果编译为 operations
  │                                      └──────────────> resume_edit
  │
  └─ 普通咨询或复杂任务 ─────────────> conversation_llm
                                          │
                                          ├─ 直接回复或追问
                                          └─ load_agent_skill
                                                   │
                                                   ▼
                                               tool_node
                                                   │ 返回完整 SKILL.md
                                                   ▼
                                           conversation_llm
                                              │         │
                               resume_snapshot  resume_edit  resume_coach
                                      │              │          │
                                      └──────────────┴──────────┘
                                                   ▼
                                               tool_node
                                                   │
                                                   ▼
                                          视觉继续分析/修改预览
```

主要节点：

- `conversation_llm`：处理普通咨询和复杂任务；模型可直接回复，也可按需调用技能。
- `tool_node`：执行 Skill 加载或结构化 Tool 调用，并把返回候选交给预览状态。
- `direct_edit`：本地唯一定位字段替换、局部粗体和可解析排版修改；它只负责确定操作，随后显式调用 `resume-edit` 生成正式候选。

全面诊断是主对话中的一次性分析，不创建粘性模式；JD 对照保留独立任务上下文，但只有需要多轮取证时才按需进入教练 Skill。深度打磨 Command 显式激活教练 Skill，普通对话则可在用户明确要求时进入，或由 Agent 先征得用户同意后进入。

## 三个标准 Agent Skills

项目级 Skill 位于 `.agents/skills/`，每项能力都是符合 Agent Skills 开放格式的独立目录，包含带 YAML frontmatter 的 `SKILL.md`。入口脚本与输入/输出 schema 是 ResumeBranch 为可执行业务能力增加的运行时扩展。

后端的 `SkillRuntime` 启动时扫描 `.agents/skills/*/SKILL.md`。模型初始只看到名称和描述；隐式发现某项能力后，通过 `load_agent_skill` 在当前 Agent 工具消息链中读取完整 `SKILL.md`，随后才暴露该 Skill 的结构化 Tool。当应用路由已经明确选定一项 Skill 时，可直接注入说明或执行入口。LangGraph Node 只负责编排和注入可信上下文，不实现 Skill 的业务算法。

模型参数与运行时上下文严格分离：模型只填写 `tool-input.schema.json` 声明的参数；当前简历、排版、修订版本、照片和渲染样式由图按 `runtime-context.schema.json` 注入，不能由模型伪造。

### `resume-edit`

实现位于 `.agents/skills/resume-edit/`，入口为 `scripts/run.py:run`，执行 Tool 为 `resume_edit`。

模型负责理解用户意图并提出结构化操作；Skill 不再次调用 LLM。它校验目标字段、布局能力和基础修订版本，在副本上应用操作，规范化候选并返回给现有确认流程。它不直接写入正式简历。

### `resume-snapshot`

实现位于 `.agents/skills/resume-snapshot/`，入口为 `scripts/run.py:run`，执行 Tool 为 `resume_snapshot`。

该 Skill 使用与正式 PDF 导出相同的渲染源生成有限页数的彩色 PNG。快照只在内存中传递，不修改简历、不创建业务文件，也不持久化图片。它只用于分页、拥挤、留白、对齐、溢出和整体观感等需要真实视觉证据的问题。

“排版建议” Command 会由后端在首次分析前强制执行该 Skill；不能只依赖前端初始 Prompt 或模型自行选择。

### `resume-coach`

实现位于 `.agents/skills/resume-coach/`，入口为 `scripts/run.py:run`，执行 Tool 为 `resume_coach`。

该 Skill 规范“确认问题—持续收集有来源的证据—由 Agent 判断证据是否充分—询问是否生成预览”的多轮过程。它只管理分析状态与一次性编辑授权，不生成候选、不保存简历。用户明确同意生成预览后，它才把已授权操作交给 `resume-edit`；生成的候选仍需经过原有确认后保存。

一个深度打磨任务可顺序处理多个问题。用户可用自然语言结束、暂停或跳过；是否充分、是否进入或退出由 Agent 按语义判断，不使用问题数或关键词阈值。

## 简历数据边界

`backend/resume_schema.py` 定义系统内部唯一的持久化简历 Schema，并通过 `validate_resume_data()` 统一验证和序列化数据库数据、修改候选、翻译结果及导出输入。运行时验证不迁移旧字段，也不根据内容猜测栏目归属。

文件解析结果只在 `backend/import_contract.py` 中执行导入适配、内容块整理、导入字重规则和未知原栏目保留，随后进行一次最终 Schema 验证和导入质量检查。导入适配不会进入数据库读取、版本恢复或渲染路径。

## 上下文与记忆

Harness 负责把本轮需要的信息组装给 Agent：

- 当前简历的结构化内容和排版配置。
- 当前岗位 JD 与任务信息。
- 当前对话窗口的近期消息、摘要和分层记忆。
- 修改中的修订版本、预览状态和占用状态。
- 必要时生成的页面视觉快照。

主对话和命令对话使用不同的上下文标识，消息历史与待确认状态不会相互混入。普通对话固定保留最近 5 个带 `round_id` 的完整轮次；每轮包含用户输入、有效助手回复和最终结果状态，确认、选择性接受、拒绝及确认后的撤回都回写原轮次，不额外占用轮次。更早轮次的语义内容与已有摘要增量合并为一份不超过 1200 字符的滚动摘要。Skill 加载、原始工具结果、生成进度和预览成功说明不作为独立对话内容持久化。教练 Skill 的当前问题、完整证据、阶段结论和待解决问题独立保存，每轮在 Skill 激活时完整注入，不受普通对话压缩窗口影响。

Harness 按正常时间顺序向模型提供最近五轮，并在每轮末尾标注 `answered`、`failed`、`noop`、`preview_pending`、`rejected`、`saved` 或 `undone`。撤回只把所属修改轮次更新为 `undone`，不再通过 `last_undone_edit`、`edit_intent_state` 或最近编号建议等旁路向系统提示额外注入旧内容。更早轮次进入摘要时，普通讨论由模型压缩为稳定事实、偏好和结论，修改轮次则由确定性程序保留请求、变更和最终结果，并继续保持原时间顺序；当前简历和真实待确认记录始终是状态事实来源。

主对话是每个简历版本唯一、长期存在的上下文。用户可通过“重新开始”重置它的消息、摘要、上下文元数据、未确认候选和主对话 Skill 状态；主对话标识保持不变，简历、JD、排版、修订版本和上传原文件不受影响。命令对话仍通过关闭后重新开启获得新上下文。

## 状态存储边界

| 状态 | 存储位置 | 说明 |
|---|---|---|
| 用户、项目、简历、JD、对话 | SQLAlchemy 业务数据库 | 单用户配置（源码或安装包）为 SQLite，多用户配置为 MySQL |
| 导入原文件 | `data/source_documents/` 或容器应用数据卷 | 用于查看原版和继续处理 |
| Agent 对话记忆 | SQLAlchemy `agent_memory_states` | 单份滚动摘要加最近五个完整结构化轮次；每个确认生命周期通过 `round_id` 归属原轮次 |
| Agent Skill 私有状态 | SQLAlchemy `agent_skill_states` | 按用户、任务、会话和 Skill 隔离；教练证据不混入普通摘要 |
| 运行中的临时预览 | 图状态与数据库中的确认元数据 | 确认、取消或失效后清理 |
| 页面视觉快照 | 内存 | 默认不持久化 |

`pending_confirmation` 只表示已经生成、等待最终保存确认的修改候选；教练阶段、证据和预览授权只存在于 `resume-coach` 私有状态，二者不再复用同一工作流字段。

## 确认、过期检测与并发

修改请求无论来自模型、教练授权、聊天内确定性解析，还是“直接修改” Command，都会先形成结构化 operations，再由 `resume-edit` 生成候选预览。前端的接受、选择性接受和拒绝统一提交给 `/confirm`；该端点是唯一允许应用候选、写入简历/排版、记录修订和释放占用的入口。

模型输出不能证明修改候选已经生成。SSE 只有在 `pending_confirmation` 校验并成功写入数据库后，才由后端发送统一的预览成功说明和确认事件；没有真实确认状态时，模型自行生成的“已生成预览”“右侧已显示预览”等文字会被拦截，不进入界面或长期记忆。

候选预览前会记录由内容摘要和排版摘要组成的 `base_version`。用户确认时按候选实际涉及的持久化范围再次比较：仅内容候选检查内容摘要，仅排版候选检查排版摘要，组合候选检查两者。

- 一致：保存候选数据，产生新的修订版本，并保留撤销能力。
- 不一致：拒绝旧修改，返回统一中文提示，并让前端重新加载数据库中的正式简历。

同一简历的修改采用数据库级占用记录做串行化，覆盖以下来源：

- 主对话与命令对话同时请求修改。
- 同一浏览器的多个标签页。
- 多个后端请求或进程。

占用期间，另一个修改请求会收到“正在修改”类中文状态；普通咨询仍可继续。前端只用对话标签旁的状态灯展示少见的占用和待确认状态，不额外挤占页面空间。

多用户模式还实行单账号单活跃会话：同一账号在新设备登录后，旧会话在下一次请求时收到明确的重新登录提示。同一浏览器共享当前凭据的多个标签页仍需依赖上述简历修改锁，而不是依靠登录限制规避并发。

## 对外标识边界

Prompt 只声明通用规则：不得向用户暴露内部协议、字段路径、节点名、工具名或状态码。它不穷举所有英文标识。

可靠边界由三层共同保证：

1. 工具和节点返回结构化内部结果。
2. 后端在响应边界映射状态、错误和组件名称。
3. 前端只展示统一中文文案，并对异常响应使用中文兜底。

日志、测试和代码中可以保留稳定的英文内部标识，但弹窗、状态提示和正常对话回复不应直接显示这些标识。

## 兼容与演进约束

- 前端只依赖公开的 SSE 事件、确认结果和业务 API，不直接依赖图内部节点名。
- 增加技能时应保持“模型理解意图、技能确定性执行、确认后持久化”的边界。
- 增加新的直接修改语法时，只接受可保留格式的精确原文；多处匹配交由用户在候选预览中选择，语义或目标不明确的请求继续交给 Agent。
- 修改 Skill 私有状态结构时，应同步 schema、持久化测试和待确认数据边界。
- 架构变更必须同步 `docs/testing.md` 中的自动与人工验收项。
